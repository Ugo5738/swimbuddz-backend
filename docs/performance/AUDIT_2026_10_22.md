## Architecture verified from code

* Frontend: Next.js **14.2.33**, React 18.2, App Router; predominantly client-side protected pages, Supabase SSR middleware, shared fetch wrapper, useApi and some React Query. Netlify configuration proxies APIs to api.swimbuddz.com and caches versioned static assets. Middleware verifies Supabase user, then non-admin member status before rendering. Client layout/session, layout profile and page-specific fetching follow.
* Backend: FastAPI, async SQLAlchemy/psycopg, PostgreSQL, domain services behind an HTTP gateway. Django and Celery are not the active stack. Background tasks use **ARQ/Redis**, including separate heavy media/AI workers. JWT validation and permissions stay in domain services.
* Database: connection pooling with configurable limits on direct hosts; NullPool and prepared statements disabled for Supabase PgBouncer. No evidence yet establishes a missing index, lock bottleneck or database saturation.
* Infrastructure: Docker Compose production config, gateway two workers, Redis persistence and health checks; configured topology is observable, actual regions/capacity/utilization are not. Do not increase resources on this evidence alone.

The source inventory contains **298 frontend page files**, **1,041 backend OpenAPI paths** and **1,232 documented HTTP operations**. The older route-reference document understates the current surface. The complete discovered page list is saved beside this local report as `route-inventory.md`; inventory alone does not constitute browser validation of each page.

Typical protected action: click → React acknowledgement → Next route request → middleware Supabase verification → member profile/access decision → route rendering/hydration → layout/page requests → gateway → domain JWT/permissions → SQL and internal APIs → rendering. Middleware, gateway, DB and browser timings are separate, sometimes overlapping stages; do not add overlapping spans together.

## Roadmap and budgets

1. Immediate: implement F1–F5, regression tests and reproducible synthetic benchmark. Use local fixtures and fake service waits; report these separately from end-user metrics.
2. Short term: F6/F7, authenticated staging browser runs; measure session-list filters and Vault query counts with representative data. Do not add indexes without query plans. Pay attention to billing's per-enrollment detail fallback and long financial-return polling.
3. Operations: collect CPU/RSS, event-loop lag, database pool utilization/locks, PgBouncer waits, Redis/ARQ queue age and worker occupancy. Verify geographic placement and static/media cache behavior before changing capacity. Requires read-only telemetry/staging access; no live changes implied.
4. Monitoring: retain request IDs and gateway spans; emit route-template slow events without query/body/token data; aggregate p50/p95/p99 and 5xx by route. Establish opt-in/sampled RUM through an approved existing analytics collector before adding a new ingestion service. No user identity, URL query or financial detail in performance events.

Initial budgets (targets, not results): feedback ≤100ms, INP ≤200ms, LCP ≤2.5s, routine read APIs p95 ≤500ms subject to per-operation validation. Track cold/warm and device/network separately. Alert only on sustained regressions (e.g. 15-minute p95 > budget and minimum sample count), not single slow requests. Complex reports/uploads need individual budgets.

## Implemented changes (F1–F5)

* Frontend admin dashboard: independent abortable useApi reads; only stats gate the page. Optional panels have their own loading/error/retry states and Flywheel starts immediately. The critical stats failure also offers Retry.
* Frontend member dashboard: a shell-scoped typed MemberProfileContext shares the layout's existing request. Layout navigation/payment refresh behavior is retained. Attendance/announcements use abortable useApi; failure recovery and attendance-before-discovery gating are tested. The profile is discarded on shell unmount. There is no global financial/profile cache.
* Backend dashboard: three stats calls run concurrently; member dashboard validates the required profile first, then fetches its independent optional sections concurrently. Dependencies, HTTP auth forwarding and graceful partial responses are retained.
* Navigation component: lifecycle tests cover feedback before route completion, pathname/query completion, history, timeout, unmount and modified clicks. Earlier helper tests now prevent jsdom's attempted native navigation.
* Shared API monitoring: successful requests over SLOW_REQUEST_THRESHOLD_MS (default 500ms; a diagnostic threshold, not an SLA for every route) emit structured warnings. Completed-request logs carry route templates rather than actual resource paths, omit raw query values, retain duration/status/request IDs. Every observable app response adds Server-Timing; gateway uses a distinct span name. These are overlapping server-to-headers spans, excluding stream transfer, not DB-only or end-to-end durations. Existing exception logging remains in place.
* CI: run gateway regressions, generate the synthetic orchestration benchmark and upload its JSON. Concurrency is enforced with dependency barriers rather than fragile wall-clock assertions. Existing frontend CI already runs the added component tests.

No schema, API payload, dependency, payment mutation, entitlement policy or production infrastructure change is needed. Backend and frontend changes can be reviewed independently; both target develop. No deployment is performed.
